## 2. 背景与目标

现有业务系统已经记录出库、到仓、上架等业务事实，但缺少一套面向海外仓运营主管的监控、预警与辅助判断系统。本项目的目标不是替代业务系统，也不是承接处理闭环，而是在不回写业务事实的前提下，快速交付一套轻量监控产品，帮助主管及时发现风险、安排资源并降低客诉风险。

本技术方案评审稿用于明确 MVP 阶段的系统形态、技术选型、模块边界、数据接入方式、认证授权方式、开发与上线环境策略，为后续研发实施、接口设计和表结构设计提供统一基线。

## 3. 技术方案结论

本项目采用“独立轻量监控子系统 + 模块化单体架构”方案。

最终技术路线如下：

- 前端：Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router + Axios + ECharts
- 后端：.NET 10 + ASP.NET Core Web API
- 内部数据库访问：EF Core 10 + 实体映射 + LINQ
- 外部业务系统只读库访问：Dapper + 手写 SQL
- 调度组件：Hangfire
- 正式目标数据库：SQL Server
- 本地辅助开发数据库：SQLite
- 缓存与幂等：Redis
- 日志：Serilog
- 接口校验：FluentValidation
- 部署方式：Nginx + 前端静态资源 + .NET API + SQL Server + Redis

本方案保持以下核心边界：

- 监控系统为独立子系统，不嵌入业务系统主工程
- 监控系统只读取业务系统数据，不回写业务事实
- 前端和提醒均基于监控系统内部的标准化结果和计算结果，不直接查询业务系统原始表
- 认证与权限复用业务系统现有接口，不单独建设用户中心

## 4. 设计原则

### 4.1 读写职责分离

- 业务系统只读库只负责提供业务事实数据
- 监控系统内部数据库负责保存快照、风险结果、提醒记录、配置和日志

### 4.2 正确性优先于实时性

- 本项目为小时级刷新，不追求秒级实时
- 规则正确、提醒不误发、不漏发优先于刷新速度

### 4.3 模块化单体优先

- MVP 阶段不拆微服务
- 通过模块边界和目录结构保持可维护性，避免过早分布式化

### 4.4 结果统一口径

- 首页、明细页、提醒消息统一基于同一套风险结果与聚合结果
- 避免页面口径与提醒口径不一致

### 4.5 本地开发简化，不改变正式目标

- 本地允许使用 SQLite 跑通内部库和基础流程
- 测试、联调和上线的最终数据库兼容性验证一律以 SQL Server 为准

## 5. 总体架构

系统总体分为以下 7 个技术模块：

1. 认证与权限适配模块
2. 外部业务读库接入模块
3. 标准化快照与存储模块
4. 监控规则计算模块
5. 查询聚合模块
6. 提醒与配置模块
7. 诊断与运维模块

整体数据流如下：

业务系统只读库
-> 增量抽取
-> 标准化快照表
-> 风险计算
-> 风险结果表 / 首页聚合结果
-> 首页与明细页接口
-> 外部提醒发送

整体访问流如下：

用户登录
-> 监控系统认证接口
-> 认证适配层调用业务系统认证接口
-> 返回 token
-> 前端使用 token 获取权限
-> 基于菜单权限和按钮权限渲染页面

## 6. 前端技术方案

### 6.1 选型结论

前端正式采用以下技术栈：

- Vue 3
- TypeScript
- Vite
- Element Plus
- Pinia
- Vue Router
- Axios
- ECharts

### 6.2 选型理由

- 首页、明细页、配置页均属于典型后台监控系统场景，适合采用组件化开发
- 三类异常清单、筛选栏、分页、状态标签、图表等能力具备高复用需求
- 后续大概率扩展数据异常页、更多筛选项、更多配置项与权限控制，Vue 3 更利于长期维护
- TypeScript 可降低接口字段错用和页面状态混乱风险
- Element Plus 可快速支撑后台管理界面的大部分组件需求

### 6.3 前端工程结构建议

```text
frontend/
  src/
    pages/
      dashboard/
      anomalies/
        outbound/
        inbound/
        shelving/
      settings/
        alerts/
      login/
    components/
      cards/
      tables/
      filters/
      charts/
      states/
    services/
    stores/
    router/
    types/
```

### 6.4 前端职责边界

- 负责展示、筛选、分页、图表渲染、菜单渲染、按钮显隐与登录态维护
- 不在前端重复实现业务规则判断，风险结果以后端返回为准
- 空状态、加载状态、错误状态统一组件化

## 7. 后端技术方案

### 7.1 选型结论

后端正式采用以下技术栈：

- .NET 10
- ASP.NET Core Web API
- EF Core 10
- Dapper
- Hangfire
- Redis
- Serilog
- FluentValidation

### 7.2 选型理由

- ASP.NET Core Web API 足以承接接口服务、后台任务、认证适配与提醒能力
- EF Core 10 适合内部数据库实体建模、结果存储、配置管理与查询服务
- Dapper 更适合对外部业务只读库执行复杂抽取 SQL
- Hangfire 适合管理小时级同步、规则重算、提醒扫描和重发任务，且有可视化任务面板
- Redis 用于缓存、幂等控制和分布式锁
- Serilog 用于结构化日志，便于追踪同步、计算、提醒问题

### 7.3 后端工程结构建议

```text
backend/
  src/
    Api/
    Application/
    Domain/
    Infrastructure/
```

### 7.4 后端职责边界

- API 层：Controller、认证中间件、参数接收、返回 DTO
- Application 层：同步编排、规则计算、查询服务、提醒服务、配置服务
- Domain 层：核心实体、状态机、时效计算规则、权限码定义
- Infrastructure 层：EF Core、Dapper、Hangfire、Redis、业务系统接口适配、企业微信/邮件适配

## 8. 认证与权限方案

### 8.1 设计原则

- 不自建独立用户中心
- 复用业务系统现有登录与权限接口
- 监控系统后端增加认证与权限适配层，屏蔽业务系统接口细节
- 菜单权限与按钮权限同时支持
- 前端负责展示层控制，后端负责接口级权限校验

### 8.2 正式认证流程

1. 前端调用监控系统登录接口
2. 监控系统认证适配层调用业务系统登录接口
3. 登录成功后返回 token
4. 前端携带 token 请求权限接口
5. 后端基于 token 获取或映射菜单权限与按钮权限
6. 前端基于权限渲染菜单、路由与按钮
7. 后端接口继续按权限码进行二次校验

### 8.3 测试阶段认证规则

测试阶段先使用固定模拟认证，便于前后端独立开发与联调：

- 用户名：admin
- 密码：admin
- 登录成功返回 token
- token 校验通过返回 200
- 权限通过 token 获取，返回菜单权限和按钮权限

### 8.4 认证接口建议

- `POST /api/auth/login`
  - 输入：`username`、`password`
  - 输出：`token`、`tokenType`、`expiresIn`、`userId`、`userName`
- `GET /api/auth/validate`
  - 输入：`Authorization: Bearer token`
  - 输出：token 有效返回 200，无效返回 401
- `GET /api/auth/permissions`
  - 输入：`Authorization: Bearer token`
  - 输出：`menuPermissions`、`buttonPermissions`

### 8.5 权限模型建议

菜单权限建议首版包含：

- `dashboard`
- `anomaly-outbound`
- `anomaly-inbound`
- `anomaly-shelving`
- `settings-alerts`

按钮权限建议首版包含：

- `anomalies-search`
- `anomalies-reset`
- `anomalies-export`
- `settings-alerts-save`

### 8.6 前端权限控制要求

- 路由守卫：无 token 或 token 无效时跳转登录页
- 菜单动态渲染：按 `menuPermissions` 控制显示
- 按钮显隐控制：按 `buttonPermissions` 控制按钮显示与可操作状态
- 统一 401 处理：清空登录态并返回登录页

### 8.7 后端权限控制要求

- 所有受保护接口必须校验 token
- 配置保存、导出等敏感操作必须做按钮级权限校验
- 后端权限校验是正式安全边界，不能仅依赖前端隐藏按钮

## 9. 数据访问策略

### 9.1 总体结论

- 监控系统内部数据库：EF Core 10 + 实体映射 + LINQ
- 外部业务系统只读库：Dapper + 手写 SQL

### 9.2 内部数据库访问策略

内部数据库承担以下职责：

- 保存标准化快照
- 保存风险结果
- 保存首页聚合结果
- 保存提醒事件
- 保存配置数据
- 保存同步日志与数据异常

该部分由 `MonitoringDbContext` 统一管理，使用实体模型、配置映射和 LINQ 查询完成日常读写。

### 9.3 外部业务只读库访问策略

外部业务只读库承担以下职责：

- 提供出库订单业务事实
- 提供入库单业务事实
- 提供箱级与上架业务事实
- 提供 ETA、重量、体积等预估基础数据

该部分不引入真正的 EF Core `ReadDbContext`。正式实现建议采用以下结构：

- `BusinessReadConnectionFactory`
- `BusinessReadQueryService`
- `BusinessReadRepository`

原因如下：

- Dapper 的核心是连接与 SQL，不需要 EF Core 的工作单元模型
- 外部表结构不受本系统控制，适合直接按 SQL 抽取
- 可避免团队误将外部只读库访问理解为系统内部持久化上下文

### 9.4 外部读库访问约束

- 只使用只读账号
- 不允许对业务库执行 migration
- 不允许前端直接访问业务系统库
- 增量抽取优先按更新时间、业务日期、状态进行限制，避免整库全量扫描
- 复杂 SQL 统一集中管理，不散落在业务逻辑中

## 10. 数据库与环境策略

### 10.1 正式目标数据库

本项目正式目标数据库为 SQL Server。

原因如下：

- 与 .NET 技术栈结合成熟
- EF Core 10 与 SQL Server 官方支持完善
- Hangfire 与 SQL Server 的生产级组合成熟稳定
- 便于正式环境中统一验证迁移、索引、并发与调度行为

### 10.2 本地开发数据库策略

由于开发环境没有 SQL Server，本地开发阶段允许使用 SQLite 作为内部数据库辅助方案，用于：

- 跑通本地项目启动
- 开发内部实体模型与基础接口
- 支撑页面联调和基础流程开发

但必须明确以下限制：

- SQLite 不作为正式数据库兼容性验证依据
- 不作为正式迁移、索引、约束、任务存储验证依据
- 最终数据库行为验证一律以 SQL Server 环境为准

### 10.3 环境策略

本地开发环境：

- 内部数据库：SQLite
- 外部业务读库：Dapper 对接共享测试读库或模拟数据源
- Hangfire：开发态轻量存储

测试与联调环境：

- 内部数据库：SQL Server
- 外部业务读库：真实只读库
- Hangfire：SQL Server 存储

UAT 与生产环境：

- 内部数据库：SQL Server
- 外部业务读库：真实只读库
- Hangfire：SQL Server 存储

## 11. 调度与后台任务方案

### 11.1 调度组件

正式调度组件采用 Hangfire。

### 11.2 任务类型

至少包含以下 5 类任务：

1. 小时级增量同步任务
2. 同步后规则重算任务
3. 首页聚合刷新任务
4. 提醒扫描任务
5. 每 4 小时一次的超时汇总重发任务

### 11.3 执行链路

同步数据
-> 标准化落库
-> 风险重算
-> 首页聚合刷新
-> 提醒扫描
-> 提醒日志记录

### 11.4 调度要求

- 任务需支持失败重试
- 任务执行状态需可视化追踪
- 同步、提醒等关键任务需支持人工重跑
- 并发调度需结合 Redis 锁或任务幂等策略，避免重复执行

## 12. 核心数据模型范围

MVP 阶段建议控制在 8 到 10 张核心业务表以内，重点包括：

- 出库订单快照表
- 入库单快照表
- 箱级快照表
- 风险结果表
- 首页聚合结果表
- 提醒事件表
- 配置表
- 同步日志表
- 数据异常表

说明：

- 快照表存放业务事实的标准化结果
- 风险结果表存放当前监控判断结果
- 提醒事件表用于幂等和提醒审计
- 数据异常表用于隔离缺字段或脏数据
- 详细表结构另行形成数据库设计稿

## 13. 接口边界建议

MVP 阶段接口建议拆分为以下五组：

1. 认证接口
2. 首页接口
3. 三类明细页接口
4. 提醒配置接口
5. 诊断接口

接口设计原则如下：

- 首页接口尽量聚合返回，减少前端多次请求
- 明细页统一分页、排序、筛选协议
- 所有时间字段必须明确时区含义
- 所有状态字段统一枚举，不允许前后端分别定义
- 配置保存、导出等操作需绑定权限码

## 14. 非功能要求

### 14.1 正确性

- 所有 SLA 计算按仓库本地时间执行
- 已完成对象不得继续出现在当前异常清单中
- 缺关键字段对象不得进入业务异常清单

### 14.2 可追踪性

- 数据同步、规则计算、提醒发送均需有日志记录
- 关键任务执行结果需可回溯

### 14.3 幂等性

- 同一对象进入同一提醒状态时不能重复发送
- 重试不得造成重复消息轰炸

### 14.4 安全性

- 统一基于 token 认证
- 前后端都要参与权限控制
- 外部读库必须使用只读账号

### 14.5 可维护性

- 模块边界清晰
- 内部数据访问与外部读库访问分离
- SQL 与业务规则逻辑分离

## 15. 本期明确不做

- 不拆微服务
- 不做 Kafka、CDC、流式计算平台链路
- 不做复杂规则引擎
- 不做业务处理闭环
- 不做多仓总部总览
- 不做历史分析报表平台
- 不让前端直接读取业务系统原始数据

## 16. 风险与待确认事项

### 16.1 当前主要风险

- 外部业务只读库权限开通不及时
- 业务系统认证与权限接口契约变动
- 测试环境 SQL Server 与正式环境准备滞后
- 权限码映射与菜单结构未及时冻结
- 消息通道开通晚于联调节奏

### 16.2 需尽快确认的事项

- 业务系统只读库连接方式与字段清单
- 业务系统认证接口、权限接口字段契约
- SQL Server 测试环境申请与可用时间
- 企业微信或邮件通道的接入顺序
- 菜单权限与按钮权限的最终编码清单

## 17. 评审结论建议

本项目建议按以下结论进入研发准备阶段：

- 采用独立轻量监控子系统方案
- 前端使用 Vue 3 技术栈
- 后端使用 .NET 10 技术栈
- 内部数据库访问使用 EF Core 10 + 实体 + LINQ
- 外部业务只读库访问使用 Dapper + 手写 SQL
- 调度使用 Hangfire
- 正式数据库使用 SQL Server，本地开发辅助使用 SQLite
- 认证与权限复用业务系统接口，监控系统后端提供适配层
