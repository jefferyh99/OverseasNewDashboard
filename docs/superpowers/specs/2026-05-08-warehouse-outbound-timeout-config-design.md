# 海外仓出库超时规则按仓库配置设计

日期：2026-05-08；阶段：方案设计；状态：待评审。

## 1. 背景

现有系统对出库异常的定义偏向统一时长口径，尚未支持不同仓库使用不同的本地时区、截单时间、工作日历和超时时点。

本次讨论已经确认以下事实：

- 所有仓库的出库规则属于同一种类型。

- 差异不在规则结构，而在仓库参数。

- 出库超时必须按仓库当地时间计算。

- 海外仓需要自动处理夏令时与冬令时。

- 周六、周日和仓库当地法定节假日都要跳过。

- 法定节假日日期由系统内手工维护。

因此，本次设计目标不是引入通用规则引擎，而是在统一算法下，为每个仓库提供一组可维护的出库时效参数。

## 2. 设计目标

1. 支持按仓库维护出库超时规则。

2. 支持按仓库当地时区计算，并自动适配夏令时与冬令时。

3. 支持周末和法定节假日跳过。

4. 支持按仓库配置截单时间、超时时点、预警提前量。

5. 保持前后端现有接口和页面结构尽量稳定，优先做增量扩展。

## 3. 非目标

- 不引入多种出库规则类型。

- 不实现表达式化规则引擎。

- 不接入外部节假日服务。

- 不把仓库常规工作时间建成超时计算参数。

- 不改动入库不齐和上架异常的规则类型。

说明：德国仓当前提到的 `8:00-17:00` 仅作为业务背景，不参与超时判定。当前真正参与计算的是截单时间、承诺完成时点、预警提前量和工作日历。

## 4. 方案对比与结论

### 4.1 方案 A：统一模板 + 仓库参数

所有仓库共用同一套算法，每个仓库只维护自己的参数。

优点：

- 实现最简单。

- 测试边界清晰。

- 设置页最好维护。

- 与当前系统结构最匹配。

缺点：

- 如果未来出现完全不同的规则类型，需要再扩展模型。

### 4.2 方案 B：统一模板 + 多个行为开关

在统一模板基础上增加多个布尔开关或可选行为。

优点：

- 灵活性更高。

缺点：

- 配置理解成本上升。

- MVP 阶段容易过度设计。

### 4.3 方案 C：通用规则引擎

用 JSON 或表达式描述规则，由系统动态解释执行。

优点：

- 灵活性最高。

缺点：

- 开发、测试、排错成本最高。

- 当前业务场景明显不需要。

### 4.4 结论

采用方案 A：`统一算法 + 仓库参数`。

## 5. 统一规则模型

所有仓库统一采用以下业务模型：

1. 判断订单创建时刻对应的仓库当地日期是否为工作日。

2. 如果不是工作日，则承诺日顺延到下一个工作日。

3. 如果是工作日，则判断订单是否超过当日截单时间。

4. 未超过截单时间的订单，当天必须完成。

5. 超过截单时间的订单，顺延到下一个工作日完成。

6. 承诺完成时点由仓库独立配置。

7. 即将超时由“超时时点 - 预警提前量”计算得到。

统一算法只做一件事：根据订单创建时间和仓库配置，算出 `warningAt` 与 `overdueAt`。

## 6. 配置模型

建议在现有 `alerts` 配置基础上做增量扩展，不另起全新配置接口。

### 6.1 仓库时间配置

- `timeZoneId`：仓库 IANA 时区标识，示例 `Europe/Berlin`，用于统一把订单时间、当前时间换算到仓库当地时间，并自动处理夏令时与冬令时。

### 6.2 仓库工作日历配置

- `weekendDays`：周末日期集合，示例 `["Saturday", "Sunday"]`。

- `holidayDates`：仓库当地法定节假日日期列表，示例 `["2026-01-01", "2026-04-03", "2026-04-06"]`，由系统内手工维护。

### 6.3 出库规则配置

- `cutoffTimeStandard`：冬令时截单时间，示例 `16:00`。

- `cutoffTimeDaylight`：夏令时截单时间，示例 `15:00`。

- `overdueTime`：承诺日的超时时点，示例 `18:00`。

- `warningLeadMinutes`：即将超时提前量，示例 `60`。

说明：如果后端希望尽量少改字段结构，也可以继续沿用现有 `leadTimes` 中 `outbound` 的值作为 `warningLeadMinutes`，页面上显示为“出库预警提前量”。

### 6.4 德国仓配置样例

```json
{
  "warehouseId": "DE",
  "timeZoneId": "Europe/Berlin",
  "weekendDays": ["Saturday", "Sunday"],
  "holidayDates": ["2026-01-01", "2026-04-03", "2026-04-06"],
  "outboundRule": {
    "cutoffTimeStandard": "16:00",
    "cutoffTimeDaylight": "15:00",
    "overdueTime": "18:00",
    "warningLeadMinutes": 60
  }
}
```

## 7. 判定流程

### 7.1 时间换算

所有参与判断的时间都必须先转换为仓库当地时间。

- 订单创建时间。

- 当前时间。

- 订单实际出库时间。

夏令时与冬令时的切换不由业务手工判断，而由 `timeZoneId` 对应的时区规则自动处理。

### 7.2 工作日判断

如果订单创建日期满足以下任一条件，则视为非工作日：

- 星期属于 `weekendDays`。

- 日期命中 `holidayDates`。

非工作日下单的订单，不看当天截单时间，直接顺延到下一个工作日。

### 7.3 截单判断

如果订单创建日是工作日，则取该日适用的截单时间：

- 夏令时日期使用 `cutoffTimeDaylight`。

- 冬令时日期使用 `cutoffTimeStandard`。

判定规则：

- `orderTime <= cutoffTime`：承诺日为当天。

- `orderTime > cutoffTime`：承诺日为下一个工作日。

### 7.4 承诺时点与风险时点

承诺日确定后：

- `overdueAt = 承诺日 + overdueTime`

- `warningAt = overdueAt - warningLeadMinutes`

### 7.5 风险状态判断

仅对当前仍未出库的订单进行判断：

- 如果订单已完成出库，则不进入风险结果。

- 如果 `now >= overdueAt`，判定为 `overdue`。

- 如果 `warningAt <= now < overdueAt`，判定为 `imminent`。

- 其他情况判定为正常，不进入异常页。

## 8. 边界约定

本次设计确认以下边界口径：

1. 下单时间等于截单时间时，仍按当天处理。

2. 周五截单后下单，顺延到下一个工作日处理；如果下一个自然日不是工作日，则继续顺延。

3. 周六、周日下单，顺延到下一个工作日处理。

4. 法定节假日下单，顺延到下一个工作日处理。

5. 超时时点不是固定 `18:00`，而是仓库级配置项。

6. 即将超时不是固定时点，而是由仓库级预警提前量倒推得到。

## 9. 德国仓示例

### 9.1 夏令时工作日截单前

- 下单时间：德国当地周二 `14:20`。

- 当日截单时间：`15:00`。

- 承诺日：周二。

- `overdueAt`：周二 `18:00`。

- `warningAt`：周二 `17:00`，假设预警提前量 60 分钟。

### 9.2 夏令时工作日截单后

- 下单时间：德国当地周五 `16:30`。

- 当日截单时间：`15:00`。

- 周六、周日不是工作日。

- 承诺日：周一。

- `overdueAt`：周一 `18:00`。

- `warningAt`：周一 `17:00`。

### 9.3 法定节假日下单

- 下单日期：德国当地法定节假日。

- 当天不参与截单判断。

- 承诺日：下一个工作日。

- `overdueAt`：下一个工作日 `18:00`。

## 10. 系统落地建议

### 10.1 后端配置 DTO 扩展

建议在现有设置 DTO 上新增仓库时间和出库规则字段，而不是新增一套独立接口。

建议新增：

- `TimeZoneId`

- `WeekendDays`

- `HolidayDates`

- `OutboundRule`

其中 `OutboundRule` 包含：

- `CutoffTimeStandard`

- `CutoffTimeDaylight`

- `OverdueTime`

预警提前量可选两种实现：

- 继续复用 `LeadTimes` 中 `outbound`。

- 或显式迁移到 `OutboundRule.WarningLeadMinutes`。

如果以最小改动为优先，建议先复用现有 `LeadTimes`。

### 10.2 后端计算服务收口

不要把出库超时计算散落在多个 Controller 或多个任务中。

建议拆成两个服务：

- `WarehouseBusinessCalendarService`：判断某日是否工作日，并查找下一个工作日。

- `OutboundDeadlineCalculator`：根据订单时间和仓库配置计算 `warningAt`、`overdueAt` 和 `riskStatus`。

### 10.3 前端设置页扩展

在现有告警配置页中增加“仓库出库规则”区块，维护以下字段：

- 时区。

- 周末定义。

- 法定节假日。

- 冬令时截单时间。

- 夏令时截单时间。

- 超时时点。

- 出库预警提前量。

### 10.4 展示层保持稳定

当前前端展示使用的关键字段可以保留：

- `deadlineAt`

- `riskStatus`

- `timeValueMinutes`

- `timeValueLabel`

本次只替换这些字段的计算来源，不改变页面主结构。

## 11. 验证重点

至少覆盖以下用例：

1. 工作日截单前下单，当天 `overdueAt`。

2. 工作日截单后下单，下一个工作日 `overdueAt`。

3. 周五截单后下单，顺延到周一。

4. 周末下单，顺延到下一个工作日。

5. 法定节假日下单，顺延到下一个工作日。

6. 下单时间等于截单时间，仍按当天处理。

7. 夏令时日期命中 `cutoffTimeDaylight`。

8. 冬令时日期命中 `cutoffTimeStandard`。

9. `warningAt <= now < overdueAt` 判定为 `imminent`。

10. `now >= overdueAt` 判定为 `overdue`。

11. 已出库订单不进入异常结果。

## 12. 实施范围建议

本次只建议实现以下最小闭环：

1. 配置模型扩展。

2. 出库超时统一计算服务。

3. 出库异常页和首页改为使用统一计算结果。

4. 设置页支持维护仓库出库规则。

暂不建议在本次一并处理：

- 节假日批量导入。

- 外部节假日同步。

- 多规则类型支持。

- 入库不齐和上架规则重构。

## 13. 结论

本次方案的核心结论是：

- 出库超时规则按仓库配置。

- 所有仓库共用同一种计算模型。

- 差异通过仓库参数表达，不通过规则引擎表达。

- 德国仓当前示例可以被完整覆盖。

这能在控制复杂度的前提下，把“仓库当地时区 + 夏冬令时截单 + 工作日历 + 仓库超时时点 + 预警提前量”统一收进可维护配置中，为后续其他仓库复用打下基础。
