# Codex 命令白名单说明

更新时间：2026-05-08

## 1. 当前生效位置

- 全局命令前缀白名单：`C:\Users\admin\.codex\rules\default.rules`
- 当前项目的信任配置：`C:\Users\admin\.codex\config.toml`

说明：

- 这个项目目前已经被标记为 `trusted`
- 但“命令前缀白名单”仍然是全局保存，不是按项目单独保存

## 2. 当前已经全局放行的常用低风险前缀

这些前缀命中后，Codex 后续通常不需要再次单独向你确认：

- `git add`
- `git commit -m`
- `dotnet build`
- `dotnet test`
- `npm run build`
- `npm.cmd run build`

另外，历史上还存在一些更具体的精确规则，例如：

- `npm.cmd --prefix frontend run build`
- 某些指定测试命令
- 某些指定 `git add` 文件列表
- 某些指定 `git commit -m "..."` 提交信息

这些精确规则依然有效，只是现在又补上了更通用的一层常用前缀。

## 3. 为什么有时还是会弹确认

即使某类命令已经加入白名单，下面这些情况仍然可能再次触发确认：

- 命令没有命中白名单前缀
- 命令前面包了一层不同的启动方式
  - 例如 `PowerShell -Command ...`
- 命令里包含复杂 shell 特性
  - 管道 `|`
  - 重定向 `>`
  - 变量展开
  - 通配符
  - 多段命令拼接
- 命令本身带有更高风险
  - 删除
  - 重置
  - 拉取网络依赖
  - 推送远程仓库

## 4. 当前这套白名单的边界

这次只补了“常用且影响较少”的几类命令，没有放开的包括：

- `git push`
- `git pull`
- `git reset --hard`
- `Remove-Item`
- `npm install`
- `dotnet restore`

这些命令要么有网络影响，要么有破坏性，要么会执行更不透明的外部动作，因此仍建议保留确认。

## 5. 后续建议

如果后面你还想继续降低确认频率，建议优先按下面顺序扩展：

1. 继续补“只读类”命令前缀
   - 例如 `git status`、`git diff`
2. 再补“低风险验证类”命令前缀
   - 例如项目内固定的构建和测试脚本
3. 高风险命令不要直接做全局白名单
   - 更适合做项目级 wrapper 脚本，再单独批准

## 6. 一句话理解

当前你已经有一套“全局常用低风险命令前缀白名单”，以后像 `git add`、`git commit -m`、`dotnet test`、`npm run build` 这几类命令，理论上会比之前少很多重复确认；但复杂命令、带风险命令、或没命中前缀的命令，仍然会继续找你确认。
